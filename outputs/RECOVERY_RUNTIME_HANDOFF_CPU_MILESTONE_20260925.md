# 恢复状态机在线运行时移交接口里程碑（2026-09-25）

## 为什么需要这一层

旧 `SupervisorRuntime` 同时执行检测、动作块截断，以及简单的 hold/retreat bridge；新实现的恢复链则包含稳定等待、碰撞中心安全脱困、6D 汇合、历史状态倒序闭环回放、重新观察和有限重规划。若直接用后者替换前者，会产生两个问题：仿真专用的 MuJoCo 碰撞查询侵入通用监督器；仅观测 shadow 模式也可能意外取得控制权。

本阶段新增环境无关的 `RecoveryExecutorPort`。运行时只负责：

1. 在经过时间确认的异常发生后，冻结策略剩余动作并生成恢复请求；
2. 把异常原因、置信度、动作序号和异常前历史快照交给外部恢复适配器；
3. 外部适配器用当前机器人可获得的传感器和碰撞证据执行恢复；
4. 每批恢复动作重新提交给运行时，并继续经过原有 `InstructionGuard`；
5. 只有恢复执行器明确报告安全完成后，才开放 π0.5 重新观察和重规划边界；
6. 恢复失败或恢复动作越过硬门时锁存 safe stop。

MuJoCo oracle 不进入这个接口。未来真机只需替换外部碰撞/执行适配器，监督器的检测、控制权仲裁和安全门保持不变。

在通用端口之上又增加 `HybridRecoveryExecutorAdapter`，把已验证的 `HybridEscapeCoordinator` 终态映射到在线运行时：协调器进入 `reobserve_and_replan` 才转为待重规划；进入 `safe_stop` 则锁存停止。中间阶段仍由环境侧逐步重建物理证据，适配器不会缓存首次候选的安全判断。

## 发现并修复的安全漏洞

定向测试发现：旧 `RecoveryController` 为避免同一异常在 `REPLAN_PENDING` 阶段重复消耗预算，会抑制重复告警。如果外部恢复动作也沿用该规则，那么被指令门判为越界的恢复动作可能被当作“重复告警”后继续执行。

修复后，恢复执行器处于 ACTIVE 时，指令门具有最高优先级：任何不安全恢复动作都会立即清空队列、把执行器状态锁存为 `safe_stop`，且禁止重规划绕过该状态。

## 保持不变的行为

- 未配置恢复执行器：旧 bridge 与现有运行时行为不变；
- `control_enabled=False`：可以计算和记录假设干预，但不得请求或认领恢复控制权，也不得修改动作队列；
- 恢复动作仍使用同一指令安全门，外部执行器不能直接绕过；
- 运行时不根据仿真隐藏状态生成动作，也不伪造真机可获得的碰撞证据。

## 验证结果与边界

新增 7 项移交测试，覆盖旧行为兼容、异常请求、shadow 隔离、安全门、成功后重规划、失败后 safe stop，以及复杂协调器终态映射。完整项目回归 **393 项全部通过**。

这仍不是最终在线恢复成功率。当前完成的是生产运行时与复杂恢复器之间的安全控制权边界；下一步需要在 LIBERO 在线循环中实现环境侧适配器，把已验证的 `HybridEscapeCoordinator` 逐步物理证据接入该端口，再运行预注册的跨 suite 配对 pilot。
