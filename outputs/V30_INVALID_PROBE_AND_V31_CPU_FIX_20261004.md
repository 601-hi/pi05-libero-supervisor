# v30 无效纵向探测与 v31 CPU 修复（2026-10-04）

## GPU 轮次结论

本轮从校验过的 action-81 故障快照启动。第一次恢复完成历史回放，并在 action 312 重置策略预算、交还 π0.5；策略再次失败后进入第二次 JOIN。真实上抬一度达到约 30.79 mm，但未达到本轮约 32.76 mm 的几何目标，随后出现回落和反复停滞。三态控制器确实触发了横移动作包及 `axis_probe`，但运行中发现探测态的动作权限错误，因此实验在 action 1057 附近主动中止，未产生 `episode_end`，不能计作任务成功或任务失败。

## 为什么本轮证据无效

`axis_probe` 的研究含义应当是：短程横移之后，只执行主逃逸轴正 Z 动作，观察纵向响应是否恢复。实现却复用了普通的“上抬—历史汇合平滑交接”选择器。该选择器在逃逸完成度达到 85% 后会允许所有安全方向重新竞争，这对正常 JOIN 合理，但对因果探测不合理。

轨迹审计得到：

- 第二次恢复共有 651 个候选决策；
- `axis_escape` 438 个、`lateral_detour` 101 个、`axis_probe` 112 个；
- 112 个探测决策中有 90 个（80.4%）选择了非正 Z 候选；
- 错误候选包括 X 负向、Y 正向以及普通 direct；
- 因而旧日志中的 `axis_probe_recovered` 混入横向运动，不能解释为纵向通道恢复。

这不是视觉误判或 MuJoCo 动力学失败，而是状态机模式没有真正约束候选集合。

## v31 最小修复

轴优先选择器新增 `require_preferred_direction`。仅在 `axis_probe` 中启用：

1. 候选必须通过原碰撞硬门和目标回退门；
2. 正 Z 预测位移必须至少 0.2 mm；
3. 轴向对齐必须至少 0.20；
4. 有合格候选时只能从该集合选取；
5. 没有合格候选时返回 `None`，由控制器执行 `axis_candidate_unavailable()`，冷却刚才的横移方向并进入下一次绕行，而不是用 X/Y 冒充探测。

普通 `axis_escape` 仍保留 85% 后向历史汇合平滑交权的旧语义，因此修复只收紧探测实验，不把整个恢复器改成纯纵向控制。

## CPU 证据

- 新增两项权限测试：高完成度仍强制主轴；无主轴候选时拒绝横向兜底；
- 探测/绕行相关测试：`6 passed`；
- 确定性三态审计：`V30_STATE_MACHINE_AUDIT_OK`；
- 服务器完整回归：`541 passed in 7.63s`；
- 对无效轨迹 112 个 probe 候选集合离线重算：112 个严格正 Z、0 个横向、0 个无候选。

最后一项只能证明“在相同候选集合上权限规则正确”，不能证明正 Z 的真实响应一定恢复。下一次固定快照 GPU 轮才是 v31 的真实验证。
