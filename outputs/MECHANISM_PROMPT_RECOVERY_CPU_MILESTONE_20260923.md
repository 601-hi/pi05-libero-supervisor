# 机制化提示恢复 CPU 节点（2026-09-23）

## 本节点的目标

在不启动 π0.5、不开 GPU 的前提下，把“检测后重新调用同一个策略”升级为可审计的单次机制/阶段提示恢复，并冻结后续开发与跨套件评测计划。

## 找到的两个运行时缺陷

1. 旧 `monitoring_main.py` 用 `supervisor.recovery.replans > 0` 判断是否追加恢复提示。这意味着第一次恢复后，该 episode 后续所有普通策略请求都会持续携带恢复提示，无法实现“恢复完成后还原原任务指令”。
2. 恢复桥接动作也会产生新的监督观测，`last_intervention` 可能被桥接步骤的普通诊断覆盖。原始失败机制没有独立锁存，因此动态提示可能在真正重新请求 π0.5 前丢失。

## 修改后的闭环契约

- 接受一次 `request_replan` 时，把完整 `InterventionDirective` 锁存在 `pending_recovery_directive`；
- 桥接期间新的逐步诊断仍正常记录，但不能覆盖待执行恢复的机制；
- 仅当恢复状态为 `REPLAN_PENDING` 时，把对应提示追加到原任务指令；
- 新恢复动作块安装后立刻清除 pending directive，后续请求自动恢复原任务提示；
- 推理日志新增 `recovery_prompt_mechanism`，可以区分提示是否激活以及由哪类机制触发。

## 机制到提示及动作的分层门控

当前任务无关路由包括：

- `empty_grasp_or_miss`：重新观察目标、必要时松夹、退离并重试抓取；
- `object_loss_risk`：重新定位物体并重建稳定抓取后再运输；
- `wrong_object_control`：只在安全区释放，重新定位正确目标；
- `fixed_obstacle_or_jam`：停止沿原方向施力、移出接触并选择无碰路径；
- `policy_stall`：识别下一个未满足任务前提，从当前场景重试该阶段；
- `execution_mismatch`：重新观察机器人与场景，用短小动作避免重复原推力；
- `instruction_unsafe`：被安全守卫拒绝的动作不执行，重新生成较小安全动作；
- `unknown`：不假定具体机制，只允许短小谨慎恢复。

提示和物理原语使用不同门槛：机制提示可以保留不确定措辞；松夹/退离等会改变物理状态的动作，要求机制置信度至少0.75。低于门槛时退化为保持后提示重规划，不执行有风险原语。

## 历史闭环因果回放

对2026-09-20的20条Stage-1和10条Stage-2 control监督日志做了只读回放。路由只读取当时逐步可见的监视事件，不读取最终成功标签。

- 输入文件：30；
- 真正 `request_replan` 决策：26；
- 26/26原因均为 `policy_stall`；
- 抓空、掉落、抓错、卡住等明确机制：0；
- 新路由结果：26/26 `hold_then_replan + policy_stall prompt`；
- 低置信度危险原语：0。

这进一步确认旧闭环并非“恢复原语选错”，而是生产日志根本没有提供机制诊断，所有恢复只能从通用停滞开始。

- 定向干预与提示生命周期测试：14/14通过；

## 下一步需要GPU的内容

先在开发集比较同一初态和固定扩散噪声下的：无干预、原指令重询、机制提示重询。只有机制提示对恢复率或停滞解除有正向信号且不明显增加成功任务损害，才打开密封18对评测。明确的松夹/退离机制仍保持shadow，直到视觉/接触证据能在自然失败中产生经过真值审计的机制标签。
