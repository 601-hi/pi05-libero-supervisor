# 恢复控制权移交 GPU 验证（2026-09-26）

## 目标

验证复杂恢复协调器通过通用 `RecoveryExecutorPort` 取得控制、完成物理恢复后才开放 π0.5 重规划，而不是由实验 runner 直接查看状态机内部状态决定下一步。

## 首次复现失败与根因

按上一轮 task0/prefix60 配置复跑时，系统仅执行5个逃逸步便回到 `hold_and_settle`。新旧结果比较发现恢复起点不同：旧成功运行的初始碰撞风险约0.561，本次约0.035。runner 只调用 `env.seed()`，没有像正式 LIBERO evaluator 一样固定 NumPy 全局随机源，且结果文件未保存恢复起点，因此此前无法证明两次物理初态相同。

修复后同时固定 NumPy 与环境 seed，并记录恢复开始时的末端位置、四元数、关节位置/速度，以及仿真 qpos/qvel SHA-256。两次独立短运行的起点摘要、稳定等待、候选评分和执行响应全部逐值相同。

## 补齐中途重新稳定分支

确定性复现也暴露 runner 的控制流缺口：协调器在风险回升时正确返回 `hold_and_settle`，但 runner 原先遇到非 `safe_escape` 就结束，完全没有执行状态机已经设计的“重新稳定后继续脱困”。现在风险/响应异常后会保持夹爪状态并重新 hold，连续稳定后从当前状态重建候选；逃逸步预算和最小尺度预算仍保持有限。

接触边界附近的 MuJoCo 有符号距离还会发生软风险分支切换。本次序列中汇合误差持续下降，而软风险曾从0.035跳到0.451。原逻辑把任何窗口风险回升优先解释为执行失败，即使候选前门、实际响应和汇合进展均正常。新增保守冲突规则：只有硬门通过、汇合误差明确改善且绝对风险不超过0.65时，才将其记为 `progress_with_risk_conflict`，保持当前尺度且禁止放大；超过0.65、硬门失败或无汇合进展仍重新稳定/缩步。0.65低于既有0.85硬拒绝门，不替代硬碰撞门。

## 最终结果

同一固定起点下，修正后执行126个逃逸步，完成6D汇合与历史状态倒序回放，进入 `reobserve_and_replan`。恢复端口从 `requested -> active -> replan_pending`，π0.5推理只在端口进入 `replan_pending` 后发生。首个策略动作被拆成6个安全微步，前2步为响应窗口预热，后4步全部safe，碰撞风险约0.053。只执行一个策略动作，因此任务未完成，不把它报告为任务恢复成功。

将接口前后两次完整运行比较，触发后到重规划前的468条物理恢复记录逐值相同，证明加入控制权端口没有改变恢复物理行为。定向恢复/移交测试75项通过，完整项目回归 **396项全部通过**。

## 下一步及诚实边界

当前异常仍由 smoke 在固定 prefix 注入，历史轨迹来自已知成功轨迹，碰撞证据仍是 MuJoCo oracle；这验证的是恢复与控制权协议，不是自然失败识别率或可部署真机安全性。下一步需把环境适配器接入正式 `monitoring_main.py`，由在线监督器异常触发端口，并保证 control/treatment 共享固定初态、π0.5采样噪声和扰动身份。完成CPU接线测试后，再运行冻结的12对跨suite pilot。
